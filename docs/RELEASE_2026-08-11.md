# Metric Quest v1 — release plan and release notes

**Release date:** Tuesday, August 11, 2026
**Status:** Planned — Track A approved. No Vercel project, deployment, domain, or secret has been created by this plan.
**Release owner:** Product owner (go/no-go and Vercel account actions)
**Release captain:** person carrying out this checklist

This is the operating document for Metric Quest's first public release. It is based on the repository's actual release candidate rather than the older static-site-only wording in the README.

## Executive decision

**Decision recorded August 11: Track A — Core v1.** Do not deploy `main` unchanged: its checked-in `api/` directory contains the optional Monet tutor, which needs `MONET_CLIENT_ID` and `MONET_CLIENT_SECRET` at runtime. The release candidate must remove or hide that tutor and its API routes before Preview; no Vercel project-provided application secrets are part of this release.

The selected and deferred tracks are recorded here for future reference:

| Track | What ships | Required before go |
| --- | --- | --- |
| **A. Core v1 — selected** | The browser-local SQL game; the tutor is removed from, or hidden in, the release candidate. | A small, reviewed release change; no production secrets. |
| B. Tutor-enabled v1 — deferred | Core v1 plus the opt-in Monet tutor. | Future release only: store both values as Vercel **Sensitive** variables, register the exact callback URLs with Monet, and complete the tutor smoke test in Preview and Production. |

Do not use a hybrid: leaving the tutor visible without its credentials is a release-blocking defect. `MONET_CLIENT_SECRET` must never be committed, pasted into this document, put in a `VITE_*` variable, or shown in build logs.

## Release scope and notes

### What is new

- Metric Quest is publicly available for the first time: a browser-based SQL learning game set inside Aurora Music's corrupted mainframe.
- Learners complete the 25-mission SQL curriculum with a browser-local SQLite database; correctness is determined from the executed result table, not the query text.
- The first release includes the terminal-style game flow: title screen, avatar selection, intro/cutscene and sector transitions, sector map, glossary, local diagnostics, and multi-save local progress.
- The release contains only the reviewed five-table minimized database derivative (`Customer`, `Genre`, `Invoice`, `InvoiceLine`, and `Track`), not the original source database in `SQL Databases/`.
- Core gameplay sends no learner query, result, or progress data to a server; progress stays in that browser's `localStorage`.
- The optional Monet tutor is deliberately excluded from v1 and deferred to a future, separately approved release.

### Known first-release constraints

- Progress is local to one browser/device. Clearing browser data removes it.
- There are no accounts, cloud saves, analytics, or backend database for core gameplay.
- The default `*.vercel.app` address is sufficient for launch; a custom domain is optional and must not delay the technical release.

## Pre-release gate

All items below are required for Track A. Deferred Track B material is retained only as a future-release reference.

### 1. Freeze the candidate

1. Decide the branch inclusion table above, then create the release candidate from the approved commits only.
2. Require a clean working tree and record the exact SHA.
3. Run `npm run check` on that exact SHA. It must pass with zero lint warnings, tests, typecheck, and production build.
4. Run `pnpm audit --prod`; any finding is triaged before release. A clean audit alone is not a claim that the app is secure.
5. Review the candidate diff for accidental generated files, source database files, credentials, private URLs, and unexpected `api/` changes.

### 2. Data and secret gate

- Confirm the runtime database import is `src/assets/data/iTunes.min.sqlite`. Do not publish `SQL Databases/iTunes.sqlite` or any other instructional source material.
- Confirm `.gitignore` covers `.vercel`, `.env*`, and `.env*.local`; inspect tracked files for `.env`, key, certificate, and credential files.
- Inspect all environment-variable reads. On the current candidate they are limited to the tutor's server-side `process.env.MONET_CLIENT_ID` and `process.env.MONET_CLIENT_SECRET`.
- **Track A — required:** verify no tutor control or API route remains reachable in the release candidate. There must be no project-provided application secrets.
- **Deferred Track B:** when the tutor is reconsidered, create its two variables in the Vercel dashboard as **Sensitive**, scoped separately to Preview and Production. Enter values only in Vercel; never put them in Git, a shell history, issue, PR, chat, screenshot, or `VITE_*` variable. Register exact HTTPS callback URLs with Monet and complete the Track B smoke tests before that later release.

### 3. Vercel setup

1. Connect the correct GitHub repository to a new Vercel project and verify the project root is this repository root.
2. Confirm Vercel detects `pnpm-lock.yaml` for installation. Keep `vercel.json` as the deployment configuration: framework `vite`, build command `npm run build`, output directory `dist`.
3. Pin the Production Branch to the approved branch policy (`main` after the release candidate is merged). Protect `main`: pull request review and a passing release gate before merges. Treat any non-production branch as Preview only.
4. Do not announce, map a custom domain, or give the public URL to learners until the Preview smoke test has passed and the product owner has given the recorded go decision.
5. Keep Vercel deployment access limited to the release owner/captain. Do not enable unrelated integrations or analytics as part of this launch.

Vercel normally creates Preview deployments for non-production branches and Production deployments from the configured Production Branch. The current `api/` Tutor routes must not be present in the Track A release candidate; if they are later restored, Vercel will deploy them as functions.

## Smoke test: Preview first, then Production

Use a fresh browser profile or private window for the clean-state checks. Run the same critical path on the exact Preview commit and on the Production URL. Capture pass/fail, tester, browser/device, and any console/network error in the handoff; do not paste secrets or session cookies.

| Area | Check | Expected result |
| --- | --- | --- |
| Availability | Open the root URL, hard refresh, and navigate with a throttled/ordinary connection. | HTTPS page and all app assets load; no 404/5xx, blank screen, or uncaught error. |
| First-run path | Select **New game**, create an avatar, complete the opening sequence, and enter Sector 1. | The game reaches a playable mission with no blocked control or clipped outer page. |
| SQL loop | Run one known-correct early mission query and one invalid query. | Correct execution completes the mission; invalid SQL shows actionable feedback and does not grant credit. |
| Progress | Refresh after completion; create/switch a save slot; use a fresh profile for the default-save case. | Progress persists only in that browser; save operations have clear confirmations and no crash. |
| Core privacy | Inspect browser Network while playing core content. | No learner SQL, results, or progress are sent to an application server. |
| Accessibility | Keyboard-only pass through title actions, avatar, cutscene continue, chapter navigation, editor/run, glossary, and save controls. Test desktop and 375px/320px narrow layouts. | Visible focus, semantic controls, readable feedback, no essential color-only instruction, no page-level horizontal scroll. |
| Audio and presentation | Toggle audio/mute, transition between screens, and inspect a representative long result table. | User control works; internal panels, not the outer app, handle necessary scrolling. |
| Release artifact | Inspect the Vercel build/deployment summary and public asset URLs. | It builds the approved SHA using the configured build/output settings; the original source database is not publicly served and no secret appears in logs/artifacts. |
| Tutor exclusion | Inspect the release candidate and deployed site for tutor controls and `/api/` tutor routes. | No tutor UI, OAuth callback, chat route, secret, or Monet request is present in v1. |

### Go/no-go rule

Go only when the exact Preview commit has passed every applicable row, the credentials/data gate is signed off, and the product owner explicitly approves Production. A failed core or security row is a **no-go**; fix it in a new candidate and repeat Preview validation. Cosmetic items may be deferred only when documented with an owner and date, and only if they do not affect accessibility, learner progress, privacy, or the first-run path.

## Production release and immediate validation

1. Merge the approved candidate according to the branch policy, or promote the exact approved deployment if that is the selected Vercel workflow.
2. Confirm the Vercel Production deployment is the recorded SHA and that the default domain points to it. Add a custom domain only after this succeeds.
3. Run the Production smoke-test table above before announcing the URL.
4. For the first 30 minutes, check Vercel build logs for failed requests and repeat the root page and one mission at 5 and 30 minutes.
5. Share the production URL only after those checks pass. Record the actual announcement time, deployment URL, SHA, test evidence location, and any deferred items in the release handoff.

## Rollback and incident plan

- **Before public announcement:** stop the release, leave the production URL unshared, and fix through a new Preview candidate.
- **After announcement:** if the app is unavailable, incorrectly grades, loses progress, exposes data, or has a tutor/secret incident, stop promotion/announcement activity immediately. Record the deployment URL and time, then use Vercel's dashboard rollback to return the production domain to the last known-good production deployment.
- A rollback switches traffic quickly but does not rebuild with newly changed environment variables. For a credential incident, rotate/revoke the affected Monet credential first, then deploy a reviewed fix; do not assume rollback removes an already-exposed secret.
- On the very first production deployment there is no prior Metric Quest production version to roll back to. The emergency action is to remove the public domain/announcement and deploy the already-tested core-only candidate.
- Do not delete old Vercel deployments during the release window: they are needed for recovery and evidence.

## Post-implementation validation and handoff

Within one business day, the release captain records:

- production URL, Vercel deployment ID/commit SHA, release time, and chosen release track;
- complete smoke-test results, including browser/device coverage;
- `npm run check` and `pnpm audit --prod` results from the released SHA;
- the database provenance/minimization confirmation;
- confirmation that no Track B/Monet secrets, Tutor routes, or third-party tutor requests were included in v1;
- review of Vercel error logs at launch, +30 minutes, and after the first real learner session; and
- a short issue list with owner, severity, and planned fix/release for every non-blocking finding.

This validation confirms a smooth first release without quietly changing the product's boundaries: executed-result grading stays local, the source database stays private, and any optional server-side tutor is explicitly configured, tested, and disclosed.
